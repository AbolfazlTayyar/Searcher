# Searcher

اپلیکیشنی برای جست‌وجو و فیلتر روی یه دیتاست حدوداً ۳۳۶ تایی از پروفایل‌های لینکدین. بک‌اند با FastAPI نوشته شده، دیتا توی Elasticsearch نگه‌داری می‌شه و فرانت‌اند هم React + TypeScript.

## اجرا

```bash
docker compose up --build -d
```

همین یه خط کافیه. Elasticsearch بالا میاد، دیتاست ایندکس می‌شه، و بعدش بک‌اند و فرانت‌اند هم اجرا می‌شن.

- فرانت‌اند: http://localhost:4173
- API: http://localhost:8000
- Elasticsearch: http://localhost:9200

ایندکس کردن یه سرویس جدا به اسم `ingest` توی `docker-compose.yml` هست که خودش اجرا می‌شه و بک‌اند هم صبر می‌کنه تا تمومش کنه. اگه یه وقت خواستید دوباره ایندکس کنید (مثلاً دیتاست عوض شد)، کافیه `docker compose up --build ingest` رو بزنید — هر بار از صفر می‌سازه، پس تکرار کردنش هیچ مشکلی نداره. نیازی هم نیست چیزی رو لوکال نصب کنید، نه `uv` نه `npm`. تنظیمات هم از طریق env variables میاد، توی `.env.example` توی ریشه‌ی ریپو همه‌شون نوشته شده.

## معماری

سه تا سرویس که توی `docker-compose.yml` به هم وصلن:

**Elasticsearch** — تک‌نود، و تنها جایی که دیتا نگه‌داری می‌شه.

**بک‌اند FastAPI** — مسیرها (`routes/search.py`) فقط پارامترها رو می‌گیرن و می‌فرستن به `search_service.py`. اونجاست که کوئری‌های ES ساخته و اجرا می‌شن، با یه کلاینت async که تزریق شده.

**فرانت‌اند React + TypeScript** — یه سرچ‌بار، دو تا فیلتر، و لیست نتایج. با TanStack Query و یه دیبانس روی اینپوت که هر کیبورد زدن یه ریکوئست نزنه.

چرا پایگاه‌داده‌ی جداگانه نذاشتیم؟ چون این دیتاست فقط یه‌بار نوشته می‌شه و بعدش فقط خونده می‌شه — یعنی اون سناریویی که واقعاً به یه دیتابیس رابطه‌ای نیاز داری (نوشتن مکرر، تراکنش، این‌جور چیزا) اینجا اصلاً پیش نمیاد. Elasticsearch خودش جست‌وجوی متنی، فیلتر دقیق، و صفحه‌بندی رو خوب انجام می‌ده. اضافه کردن یه دیتابیس دوم فقط یعنی باید دو تا سیستم رو با هم sync نگه داری، بدون اینکه واقعاً چیز جدیدی بهت بده.

## منطق جست‌وجو و فیلتر

هر ریکوئست توی `search_service.py` تبدیل می‌شه به یه کوئری `bool`:

- پارامتر `q` می‌ره توی `must` به شکل `multi_match`، روی سه تا فیلد (`full_name` با وزن بیشتر، `summary`، `skills`) و روی رتبه‌بندی نتایج هم اثر می‌ذاره. اگه `q` خالی باشه، به جاش `match_all` می‌ذاریم.
- `job_title` و `skill` می‌رن توی `filter` به شکل `term`، روی زیرفیلد `.keyword` تطابق دقیق می‌گیرن و رو رتبه‌بندی هم اثری ندارن.

مپینگ ایندکس (`ingest/mapping.py`) رو دستی تعریف کردیم، نه داینامیک، چون مپینگ داینامیک زیرفیلدهای `.keyword` رو همون‌جوری که برای فیلتر دقیق لازم داریم نمی‌سازه. صفحه‌بندی هم ساده و آفست‌محوره (`from`/`size`)؛ با این حجم داده (حدود ۳۳۶ تا) صفحه‌بندی عمیق اصلاً مشکلی ایجاد نمی‌کنه که بخوایم دنبال راه‌حل پیچیده‌تر بگردیم
