# Searcher

اپلیکیشن جست‌وجو و فیلتر روی حدود ۳۳۶ پروفایل لینکدین. بک‌اند FastAPI، پایگاه‌داده Elasticsearch، فرانت‌اند React + TypeScript.

## نحوه اجرا

```bash
docker compose up --build -d   # بالا آوردن Elasticsearch، ایندکس کردن خودکار دیتاست، بعد بک‌اند و فرانت‌اند
```

- فرانت‌اند: http://localhost:4173
- API بک‌اند: http://localhost:8000
- Elasticsearch: http://localhost:9200

ایندکس کردن یک سرویس جدا (`ingest`) در `docker-compose.yml` است و خودش اجرا می‌شود؛ بک‌اند صبر می‌کند تا تمام شود. برای ایندکس دوباره (مثلاً بعد از عوض شدن دیتاست) کافی‌ست `docker compose up --build ingest` را بزنید — هر بار ایندکس از صفر ساخته می‌شود، پس تکرارش مشکلی ندارد. نیازی به نصب محلی `uv` یا `npm` نیست. تنظیمات از طریق متغیرهای محیطی انجام می‌شود (`.env.example` در ریشهٔ ریپو).

## معماری

سه سرویس که با `docker-compose.yml` به هم وصل می‌شوند:

- **Elasticsearch** — تک‌نود، تنها پایگاه‌داده‌ی پروژه.
- **بک‌اند FastAPI** — مسیرها (`routes/search.py`) پارامترها را می‌خوانند و کار را می‌سپارند به `search_service.py` که کوئری‌های ES را می‌سازد و با کلاینت async تزریق‌شده اجرایشان می‌کند.
- **فرانت‌اند React + TypeScript** — نوار جست‌وجو، فیلترها، و لیست نتایج، با TanStack Query و ورودی دیبانس‌شده.

**چرا پایگاه‌داده‌ی جداگانه نداریم:** دیتاست فقط خوانده می‌شود و فقط یک‌بار نوشته می‌شود، پس مسیر نوشتنِ مکرر که به یک پایگاه‌داده‌ی رابطه‌ای نیاز داشته باشد اصلاً وجود ندارد. جست‌وجوی متنی، فیلتر دقیق، و صفحه‌بندی — همه اینها را Elasticsearch به‌تنهایی خوب انجام می‌دهد؛ اضافه کردن یک پایگاه‌داده‌ی دوم فقط دردسر هم‌گام‌سازی می‌آورد، نه قابلیت جدید.

## منطق جست‌وجو و فیلتر

`search_service.py` هر درخواست را به یک کوئری `bool` تبدیل می‌کند:

- `q` به `multi_match` در `must` تبدیل می‌شود (روی `full_name^3`، `summary`، `skills`) و روی رتبه‌بندی اثر می‌گذارد؛ اگر `q` نباشد، `must` می‌شود `match_all`.
- `job_title` و `skill` به `term` در `filter` تبدیل می‌شوند و روی زیرفیلد `.keyword` تطابق دقیق می‌گیرند، بدون تاثیر روی رتبه‌بندی.

نگاشت ایندکس (`ingest/mapping.py`) صریح تعریف شده تا فیلدهای متنی زیرفیلد `.keyword` برای فیلتر دقیق داشته باشند — چیزی که نگاشت داینامیک به‌درستی تنظیم نمی‌کند. صفحه‌بندی آفست‌محور است (`from`/`size`)، چون با حدود ۳۳۶ سند صفحه‌بندی عمیق هیچ‌وقت گران تمام نمی‌شود.

## کیفیت داده

فایل منبع (`data/300_user_linkedin.txt`) فقط در نام‌گذاری CSV است:

1. **فیلدهای تودرتو لیترال پایتون هستند، نه JSON.** `skills`، `experience`، `education` و مشابه با `ast.literal_eval` پارس می‌شوند؛ اگر نوع پارس‌شده با نوع مورد انتظار فیلد جور درنیاید (نشانهٔ جابه‌جا شدن ستون‌ها)، فیلد غایب در نظر گرفته می‌شود.
2. **حدود ۸۱٪ از سطرها (۲۷۱ از ۳۳۶) نامعتبرند.** کوتیشن‌های بدون escape در فیلدهای متنی آزاد (مثل `summary`) بقیهٔ ستون‌های همان سطر را جابه‌جا می‌کنند. ۵۳ سطر (~۱۶٪) تعداد کل فیلدها را هم عوض می‌کنند و صرفاً با مقایسهٔ طول سطر با هدر شناسایی می‌شوند. ۲۱۸ سطر دیگر (~۶۵٪) جوری جابه‌جا شده‌اند که تعداد فیلد همان می‌ماند (یک فیلد کاما را قورت می‌دهد، یک فیلد دیگر جلوتر دو تکه می‌شود)، پس `parse_profiles` شکل تک‌تک فیلدها را هم چک می‌کند — `industry`/`job_title`/`summary` نباید لیترال پایتون یا شمارهٔ تلفن خام باشند، `summary` نباید عدد خام هم باشد، `skills` (که به‌عنوان لیستی از رشته‌ها همچنان معتبر است) نباید لیستی از شماره‌تلفن باشد، فیلدهای URL پلتفرم‌ها (`linkedin_url` و مشابه) باید دامنهٔ خودشان را داشته باشند — و اگر یکی از این‌ها جور درنیاید، کل سطر رد می‌شود، نه فقط همان فیلد. ۳۴ سطر (~۱۰٪) هم عیناً تکراری‌اند و حذف می‌شوند تا دوبار ایندکس نشوند. از ۳۳۶ سطر آخرش فقط ۳۱ تا (~۹٪) سالم می‌مانند؛ همهٔ ردشدن‌ها با شماره‌سطر و دلیلش در `backend/ingest.log` ثبت می‌شوند.
3. **خیلی از فیلدها طبیعتاً خالی‌اند** (`job_title` ~۲۸٪، `industry` ~۴۰٪). مقادیر خالی به `None` نگاشت می‌شوند و همهٔ فیلدهای `ProfileResult` اختیاری‌اند.

## تست

بک‌اند: `cd backend && uv run pytest` — پوشش جست‌وجو، فیلترها، و حالت بدون نتیجه.
فرانت‌اند: `cd frontend && npm test` — پوشش `SearchBar`، `Filters`، `ResultsList`.
هیچ‌کدام برای اجرای خود اپ لازم نیستند.
